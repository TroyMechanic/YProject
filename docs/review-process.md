# 项目定期 Review 机制

本文档定义本项目的定期审查方式。目标是持续检查代码、规则文档和实际图形结果是否一致，并基于缠论理解提出可讨论的建议。

## 1. 基本原则

Review 必须区分两类结论：

### 已确认规则检查

检查代码是否正确实现 `docs/chan-rules.md` 中已经由用户确认的规则。

发现不一致时，可以作为缺陷提出，并给出代码位置、复现数据和修复建议。

### 候选规则建议

基于对缠论的理解，提出当前项目可能缺失、存在歧义或值得讨论的规则。

候选建议必须明确标记为：

```text
待讨论
```

未经用户确认，不得：

```text
修改算法代码
修改现有规则口径
写入 docs/todo.md
把建议描述成确定结论
```

## 2. Review 触发方式

建议采用两种触发方式。

### 固定周期 Review

建议每月执行一次完整 Review。

AI 无法在没有外部触发的情况下自行定时运行，因此需要以下任一方式触发：

```text
用户每月主动发起“执行项目 Review”
日历或任务工具定期提醒用户
本地定时任务或 CI 定期启动 Review 流程
```

当前项目先采用人工触发，不新增自动化调度。

### 事件触发 Review

发生以下情况时，建议立即执行专项 Review：

```text
修改包含关系规则
修改顶底分型规则
修改同类分型过滤规则
修改成笔规则
新增缠论层级或强弱判断
行情源或复权口径变化
用户发现图形结果与预期不一致
连续完成三次以上规则改动
```

## 3. Review 范围

每次完整 Review 至少检查以下内容。

### 规则与代码一致性

```text
docs/chan-rules.md 是否与 chan_analyzer.py 一致
默认参数是否在后端、前端和文档中一致
严格大于/小于等边界条件是否一致
原始 K 线序号和标准 K 线序号是否混用
解释文案是否准确反映实际判断条件
```

### 算法正确性

```text
包含关系识别
上涨/下跌方向判定
向右合并
连续包含处理
顶分型识别
底分型识别
同类分型取舍
标准 K 线最小间隔
成笔价格范围
最后一笔确认状态
```

### 数据一致性

```text
原始 K 线 CSV 是否合法
open/close 是否位于 low 和 high 之间
日期是否有重复或乱序
不同周期数据是否隔离
分型和笔 CSV 是否由当前规则重算
图表数据和解释数据是否来自同一批结果
```

### 样本验证

至少选取以下样本：

```text
一段连续包含 K 线
一个顶分型
一个底分型
一组连续同类顶分型
一组连续同类底分型
一笔向上笔
一笔向下笔
一个不能成笔的边界案例
当前最后一笔
```

每个样本都应记录：

```text
股票代码
周期
日期范围
输入 K 线
标准 K 线
计算结果
预期结果
结论
```

### 测试与构建

```bash
cd backend
PYTHONPATH=. pytest
```

```bash
cd frontend
npm run build
```

涉及前端交互时，还应在浏览器中验证：

```text
K 线 hover 信息
分型点击解释
笔点击解释
日K / 周K / 月K切换
不同屏幕宽度下是否遮挡
```

## 4. 缠论理解审查

在代码一致性检查之外，可以基于缠论理解审视：

```text
规则口径是否完整
当前定义是否存在多种流派解释
某条规则是否会产生明显异常图形
是否缺少关键边界条件
现有解释是否足够支持人工核验
下一阶段学习时值得优先确认的问题
```

这部分只提出建议，不直接改变规则。

每条建议应包含：

```text
建议标题
当前实现
观察到的问题
可能的规则口径
对现有结果的影响
需要用户确认的问题
```

## 5. Review 报告

每次 Review 在以下目录保存一份报告：

```text
docs/reviews/YYYY-MM-DD.md
```

报告按严重程度排列：

```text
P0 结果完全错误或数据损坏
P1 规则实现错误，会显著改变分型或笔
P2 边界条件、解释或数据一致性问题
P3 可维护性、测试覆盖和体验建议
```

报告模板：

```markdown
# 项目 Review - YYYY-MM-DD

## Review 范围

## 已确认规则问题

## 数据与图形问题

## 测试缺口

## 待讨论的缠论建议

## 验证结果

## 本次结论
```

如果没有发现问题，也要明确记录：

```text
本次未发现已确认规则的实现偏差
```

并列出仍未覆盖的风险。

## 6. Review 后处理

Review 报告中的事项按以下方式处理：

```text
确认的代码缺陷：修复代码、补测试、同步文档、重算数据
用户确认的新规则：更新 chan-rules.md 后再实现
用户明确计划实现的功能：写入 todo.md
尚未确认的建议：仅保留在 Review 报告中
已完成的用户可见功能：更新 features.md
```

## 7. 推荐执行口令

用户可以使用以下口令启动流程：

```text
执行一次完整项目 Review
Review 最近的缠论规则改动
Review 立讯精密日K最近三个月的分型和笔
只检查规则文档和代码是否一致
```


## 8. v2.0.0 后的修改约束

持续修改执行 `docs/development.md`。本次用户明确授权按助手理解完善规则；具体选择记录在 `docs/decisions/0001-versioned-rules.md`，不自动授权所有未来建议。

Review新增检查：规则目录版本与文档/固定样本一致；图表展示的实际设置与候选控件值区分；完整快照的输入、代码、规则和结果指纹；日期裁剪不得覆盖全历史；同步不得重置保存参数；固定输入追加时已确认几何终点稳定。中枢必须标注线段重叠模型，不能当作已完成递归走势中枢或买卖信号。

确认差异后再更新固定基线，禁止为让测试变绿直接自动覆盖预期。推送后CI执行回归与规则版本/文档检查；阻止不通过检查合并还依赖仓库分支保护设置。
